Coroutines in Unity 6: Usage & Best Practices

Updated 2026-11-06

Coroutines are still fully supported in Unity 6 and remain the simplest way to spread gameplay logic over frames. For new code that waits on I/O, returns a value, or needs try/catch, Unity 6's Awaitable is usually the better tool (see the last section).

How a coroutine works

A coroutine is a method that returns IEnumerator and pauses at each yield return. Unity holds the paused method and resumes it later, at a point in the frame set by what you yielded.

  • It is not a thread. Everything runs on the main thread, so you can touch any Unity API inside it.
  • It is owned by the MonoBehaviour that started it. If that GameObject is deactivated or destroyed, the coroutine dies with it.
  • Each yield return is a checkpoint. Code between two yields runs in one go, within a single frame.
using System.Collections;
using UnityEngine;

public class Blinker : MonoBehaviour
{
    [SerializeField] Renderer target;

    IEnumerator Start()          // Start itself can be a coroutine
    {
        while (true)
        {
            target.enabled = !target.enabled;
            yield return new WaitForSeconds(0.5f); // pause, resume ~0.5 s later
        }
    }
}

Where in the frame a coroutine resumes depends on its yield:

Most yields resume right after Update and before LateUpdate, so a coroutine sees the same state your Update methods just produced.

Starting and stopping

Always keep the Coroutine handle that StartCoroutine returns, and stop by handle. That is the only form that reliably stops exactly the run you started.

Coroutine fadeRoutine;

public void FadeIn()
{
    // Restart cleanly: stop any fade already running
    if (fadeRoutine != null) StopCoroutine(fadeRoutine);
    fadeRoutine = StartCoroutine(Fade(0f, 1f, 0.4f));
}

IEnumerator Fade(float from, float to, float duration)
{
    for (float t = 0; t < duration; t += Time.deltaTime)
    {
        canvasGroup.alpha = Mathf.Lerp(from, to, t / duration);
        yield return null;
    }
    canvasGroup.alpha = to;
    fadeRoutine = null;          // mark as finished
}
CallWhat it stopsNotes
StopCoroutine(Coroutine handle)That one runPreferred
StopCoroutine(IEnumerator e)The run using that exact enumerator instanceCalling StopCoroutine(Fade()) creates a new instance and stops nothing
StopCoroutine("Name")Runs started with the string overloadAvoid: no compile-time checking, one parameter max
StopAllCoroutines()Every coroutine on this MonoBehaviourOther components are unaffected

What else ends a coroutine:

  • Deactivating the GameObject (SetActive(false)) or destroying it or the component.
  • An unhandled exception inside it; the error is logged and the coroutine stops.
  • Disabling the component (enabled = false) does not stop it.
  • You cannot start a coroutine on an inactive GameObject; Unity logs an error instead.

All timed waits resume on the first frame after the time has passed, so they overshoot by up to one frame. Never yield return 0 or any other number; it boxes an int and behaves exactly like null.

Common patterns

Timed lerp with an easing curve

IEnumerator MoveTo(Transform t, Vector3 target, float duration, AnimationCurve ease)
{
    Vector3 start = t.position;
    float elapsed = 0f;
    while (elapsed < duration)
    {
        elapsed += Time.deltaTime;
        t.position = Vector3.LerpUnclamped(start, target, ease.Evaluate(elapsed / duration));
        yield return null;
    }
    t.position = target;   // snap to the exact end value
}

Sequencing steps

Yielding one coroutine from another waits for it to finish, which turns a cutscene or tutorial into readable top-to-bottom code.

IEnumerator IntroSequence()
{
    yield return MoveTo(cam, shotA, 1.5f, easeInOut); // nested: waits until done
    yield return dialogue.Show("Welcome, pilot.");
    yield return new WaitUntil(() => playerConfirmed);
    yield return Fade(1f, 0f, 0.5f);
}

Running steps in parallel, then joining

IEnumerator OpenGates()
{
    Coroutine left  = StartCoroutine(MoveTo(gateL, openL, 1f, ease));
    Coroutine right = StartCoroutine(MoveTo(gateR, openR, 1f, ease));
    yield return left;    // wait for both
    yield return right;
    audio.PlayOneShot(clunk);
}

Low-frequency polling instead of Update

Checks that do not need to run every frame (AI perception, spawn checks) can tick on a slower interval.

readonly WaitForSeconds tick = new WaitForSeconds(0.25f);

IEnumerator SenseLoop()
{
    while (true)
    {
        ScanForTargets();
        yield return tick;   // 4 times per second, no allocation per loop
    }
}

Async loading with progress

IEnumerator LoadLevel(string scene)
{
    AsyncOperation op = SceneManager.LoadSceneAsync(scene);
    op.allowSceneActivation = false;
    while (op.progress < 0.9f)        // progress stops at 0.9 until activation
    {
        loadingBar.value = op.progress / 0.9f;
        yield return null;
    }
    loadingBar.value = 1f;
    op.allowSceneActivation = true;
}

Best practices

  1. Keep the handle, guard against double starts. Starting the same coroutine twice (two clicks, two triggers) runs two copies that fight over the same values. Stop the old handle before starting a new one, as in the fade example.
  2. Cache constant yield objects. new WaitForSeconds(0.25f) allocates each time; a readonly field reused in a loop does not. yield return null never allocates. Do not share WaitUntil/WaitWhile instances between coroutines running at the same time.
  3. Start coroutines on the object whose lifetime they belong to. otherBehaviour.StartCoroutine(...) ties the coroutine to that other object, so it keeps running after the caller is destroyed, or dies when the other object is disabled. A long-lived manager is fine for global work; per-object effects belong on the object.
  4. Use Time.deltaTime accumulation, not repeated short waits, for smooth motion. A loop of WaitForSeconds(0.01f) still runs at most once per frame and drifts. Accumulate elapsed time and yield return null.
  5. Pick scaled or unscaled time on purpose. Gameplay respects Time.timeScale; pause menus and UI need WaitForSecondsRealtime and Time.unscaledDeltaTime, or they freeze with the game.
  6. Snap to the final value after a lerp loop. The last frame rarely lands exactly on t = 1.
  7. Keep each coroutine small and named for what it does. Compose them with nested yields instead of writing one long state machine.
  8. Clean up on disable. Coroutines survive enabled = false, so stop them in OnDisable if the component should go quiet when disabled.
void OnDisable()
{
    if (fadeRoutine != null) { StopCoroutine(fadeRoutine); fadeRoutine = null; }
}

Coroutines vs Awaitable in Unity 6

Unity 6 ships Awaitable, a pooled awaitable type for async methods with Unity-aware waits. A common rule of thumb: coroutines for frame-driven effects and sequences, Awaitable for I/O, loading, and anything that returns a value. Unity's manual says Awaitable is usually slightly more efficient than iterator coroutines, especially when the iterator yields non-null objects like WaitForFixedUpdate.

CoroutineAwaitable equivalent
yield return nullawait Awaitable.NextFrameAsync()
yield return new WaitForSeconds(1f)await Awaitable.WaitForSecondsAsync(1f)
yield return new WaitForFixedUpdate()await Awaitable.FixedUpdateAsync()
yield return new WaitForEndOfFrame()await Awaitable.EndOfFrameAsync()
yield return asyncOpawait asyncOp or await Awaitable.FromAsyncOperation(op)
(no equivalent)await Awaitable.BackgroundThreadAsync() / MainThreadAsync()
async Awaitable ShowAfterDelayAsync()
{
    try
    {
        await Awaitable.WaitForSecondsAsync(1f, destroyCancellationToken);
        panel.SetActive(true);
    }
    catch (OperationCanceledException) { /* object was destroyed */ }
}

What changes when you switch:

  • Lifetime is not automatic. An async method keeps running after its GameObject is destroyed. Pass destroyCancellationToken to waits, and use Application.exitCancellationToken for work that must stop when leaving Play mode.
  • Never await the same Awaitable twice. Instances are pooled and reused, so a second await is undefined behaviour.
  • You gain return values (Awaitable<T>), normal try/catch, and explicit thread switching for heavy work.
  • Interop: a coroutine can yield return a non-generic Awaitable, but not an Awaitable<T>.
Choose a coroutine whenChoose Awaitable when
Visual effects, tweens, cutscene sequencesLoading assets, scenes, web requests
It should die automatically with the GameObjectYou need a return value or exception handling
Existing codebase or students already use themYou want to offload work to a background thread
